# some-conveyor

> Polyhedron content conveyor — a browser extension that injects a continuously moving strip of rotating cubes into web pages, backed by a Rust/WASM state machine.

---

## Overview

`some-conveyor` is an experiment in treating browser attention as a schedulable surface.

Rather than opening a dashboard, tab, or application, the user is presented with a persistent conveyor of rotating polyhedra rendered directly into the page. Each cube acts as an independent projection surface capable of displaying dynamic content while participating in a larger scheduling system.

The extension injects a bottom-of-screen conveyor belt composed of rotating cubes. As the conveyor traverses the viewport, individual cubes rotate along one or more axes, exposing different faces according to a deterministic schedule generated by a WebAssembly state machine.

The result resembles a digital marquee composed of three-dimensional cells rather than a flat ticker.

---

## Core Concepts

### Conveyor

The conveyor is a continuously moving strip occupying a fixed region of the viewport.

Responsibilities:

- Owns layout of all cubes.
- Controls horizontal movement.
- Determines visibility window.
- Recycles cubes as they exit and enter the viewport.
- Acts as the composition root for rendering.

Conceptually:

```text
+------------------------------------------------------+
|                                                      |
|                                                      |
|                                                      |
+------------------------------------------------------+

[□] [□] [□] [□] [□] [□] [□] [□] [□] [□]
  --> --> --> --> --> --> --> --> -->
```

---

### Cube

A cube is a first-class entity.

Each cube:

- Owns six faces.
- Maintains its own rotation state.
- Can rotate around:
  - X axis
  - Y axis
  - Both axes
- Receives content assignments from the scheduler.
- Exists independently of neighboring cubes.

A cube is not merely a visual effect.

It represents a projection surface onto which scheduled content is mapped.

---

### Face

Each cube exposes six potential presentation surfaces.

```text
Front
Back
Left
Right
Top
Bottom
```

Only one face is considered active at a given moment.

Inactive faces may already contain content in preparation for future rotations.

---

### Projection

A projection is a mapping between:

```text
content -> cube face
```

Examples:

- Quote
- Note
- Reminder
- Stock position
- ERP metric
- Build status
- RSS item
- Campaign state
- Trading journal entry

The scheduler decides:

- what content appears
- where it appears
- when it appears
- how long it remains visible

---

### Schedule

The schedule is generated by a Rust/WASM state machine.

The scheduler's job is not animation.

The scheduler's job is deciding:

```text
which item
on which cube
on which face
at which time
```

Animation is simply the physical manifestation of schedule transitions.

---

## Why WASM?

Animation timing can be performed entirely in JavaScript.

The reason for WASM is ownership of scheduling logic.

The scheduler:

- generates state transitions
- performs combinatorial selection
- tracks visibility windows
- computes future projections
- remains deterministic and testable

The browser becomes a rendering host.

The Rust crate becomes the authority for scheduling.

```text
Rust
 └── State Machine
      └── Schedule

WASM
 └── Exported API

TypeScript
 └── Rendering
      └── DOM
```

## Browser Extension Model

### Background Script

Runs independently of page context.

Responsibilities:

- extension lifecycle
- storage coordination
- message routing
- future synchronization tasks

Entry:

```text
background.js
```

---

### Content Script

Injected into matching pages.

Responsibilities:

- create conveyor root
- attach shadow DOM
- render cubes
- run animations
- communicate with WASM scheduler

Entry:

```text
content.js
```

---

### Popup

Extension control surface.

Responsibilities:

- debugging
- status display
- future configuration

Entry:

```text
popup.html
```

---

## Rendering Strategy

The conveyor should behave as an overlay rather than participate in page layout.

Preferred characteristics:

- fixed positioning
- isolated styling
- shadow DOM encapsulation
- high z-index
- minimal interference with host page

Example:

```css
position: fixed;
left: 0;
bottom: 0;
width: 100%;
pointer-events: none;
z-index: 2147483647;
```

This avoids collisions with arbitrary website styles.

## Animation Model

Two independent timelines exist.

### Translation Timeline

Moves cubes across the viewport.

```text
time →
[□][□][□][□][□]
```

---

### Rotation Timeline

Rotates cubes independently.

```text
Front
  ↓
Top
  ↓
Back
  ↓
Bottom
```

The scheduler may trigger rotations based on:

- elapsed time
- campaign state
- visibility events
- content exhaustion

---

## Guiding Principle

The conveyor is not a widget.

It is a transport system.

Content does not live on a page.

Content enters a conveyor, is projected onto rotating polyhedra according to a deterministic schedule, becomes visible for a period of time, and then exits the viewport.

The cube is the cell.

The face is the projection surface.

The conveyor is the transport medium.

The scheduler is the authority.
