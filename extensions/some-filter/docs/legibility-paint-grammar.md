# Legibility audit — supported paint grammar

- **Epic:** #1347 (`TSC-SF`)
- **Story:** TSC-SF1, #1357
- **Scope:** `src/adapter/legibility-audit.ts` only — `auditLegibility`,
  `resolveEffectiveBackdrop`, `ownTextColor`, and the rendered-ness/geometry
  helpers they call. Not a grammar for `pipeline.ts`'s own vendor-evidence
  Sensor (`scan()`), which has a distinct exclusion/inheritance model for a
  distinct purpose.

## Why this table exists

Most categories below entered this module because a reviewer found a live
counterexample during `d36c575`/#1345's own review (six "round N" cycles,
one per counterexample) — not because a category enumeration existed to
check a new case against first. This table is that enumeration, so the next
gap is a designed table update, not another incident-driven round.
`legibility-audit.ts`'s own header points here. (This table's own four
review rounds while landing found seven more gaps the same incident-driven
way, one severe enough to affect how the epic's remaining stories should be
prioritized — see the Coherence check section at the bottom.)

Each row: **disposition** is `sound` (the check is exact, given its stated
boundary), `heuristic` (conservative and correct at the boundary it declares,
but not a general solution), or `unknown` (the category is not handled at
all — no test can pass or fail against it because no code path exists for
it). A `heuristic`/`unknown` disposition converging on `"underdetermined"`
is the intended, conservative outcome (Axiom C.1) — not a defect to later
"finish" into `sound` unless a bounded, provably sound extension is found.

Multiple tests may own one cell; a test may cover more than one cell (noted
where it does). Every test below lives in
`src/adapter/__tests__/legibility-audit.test.ts` unless stated otherwise.

## PG-GROUP — opacity, filter, blend mode, backdrop-filter, mask (whole-element compositing)

Every category here except `PG-GROUP-BACKDROP-FILTER` composites the
_entire_ element (background, text, and descendants together) against
whatever sits behind it — a descendant's own opaque background cannot shield
it, unlike `PG-BG-IMAGE`'s ordinary z-order — and is checked all the way to
`document.documentElement` regardless of where color accumulation itself
resolves. `backdrop-filter` is a distinct mechanism (bot-found, Codex review
of this PR): it filters the backdrop _behind_ an element, before that
element's own background/content paints on top of the result — unlike
`filter`/`opacity`/`mix-blend-mode`, a nearer descendant's fully opaque
background genuinely _can_ shield an ancestor's `backdrop-filter` from
reaching anything further out. The code checks it via the identical
unconditional code path anyway, as a deliberate over-approximation for
implementation simplicity — see its own row below, not this paragraph, for
what it actually guarantees.

## PG-SCOPE — shadow roots, iframe/cross-realm boundaries

**Corrected finding (bot-found, Codex review of this PR):** `auditLegibility`
is invoked from exactly one production call site — `pipeline.ts`'s `fire()`,
which owns the _document_ scope only. `fire()`'s own `lastRoot` is typed
`Element` and is never a `ShadowRoot`. Shadow-scoped content has an entirely
separate sense→decide→realize path (`shadow-scope-theming.ts`'s
`projectOnce()`, which calls `pipeline.ts`'s `scan()`/`decide()` directly);
it never imports or calls `auditLegibility`/`decideLegibility`/
`realizeLegibility` at all — confirmed directly, a repo-wide search finds no
reference to any of the three outside `pipeline.ts` and this module's own
tests. **Shadow-scoped content is therefore never legibility-audited in
production, full stop — not `"underdetermined"`, simply never scanned.**
This is a materially larger gap than this table's own `unknown` rows: those
are silent within an _audited_ scope; this is an entire scope class never
entering the audit. Filed as #1370 (sub-issue of this story) for
a future story to wire or explicitly scope — fixing it is outside this
documentation-only PR.

The rows below are about what happens _inside_ one call to `auditLegibility`
against the document scope — the only scope this channel currently reaches
— not about `auditLegibility` itself crossing scope boundaries.

## Cross-cutting: verdict propagation (not a `PG-*` category)

`decideLegibility` and `realizeLegibility` do not test a paint-grammar
category — they test that any `"underdetermined"` value from _either_ the
foreground or backdrop channel propagates to an explicit
`{ verdict: "underdetermined" }` action (never silently resolved as
passing), and that the `data-sw-legibility` attribute realization is a
correct, idempotent, self-clearing projection of that decision. This is
Axiom C.1's conservative-verdict-propagation invariant, cross-cutting every
`PG-*` row above rather than owned by one of them.

Owning tests: "flags a violated pair below the WCAG AA minimum"; "emits
nothing for a pair at/above the WCAG AA minimum"; "flags underdetermined
backdrops rather than silently passing them"; "flags an underdetermined
foreground (e.g. an unparseable CSS Color 4 value) even with a fully
resolvable backdrop"; "MIN_CONTRAST_RATIO matches WCAG 2.1 AA normal text
(4.5:1)"; "composites a translucent own foreground over the backdrop before
measuring contrast"; "flags a near-invisible foreground as violated — it
composites toward the backdrop it sits on"; all four `realizeLegibility`
tests ("tags every element sharing a violated key"; the zero-write no-op
case; the stale-tag-clearing case; the unrelated-attribute-preservation
case).

## PG-FG — foreground syntax, inheritance, alpha, vendor text-fill

**Resolved finding (bot-found during this table's own review, fixed in
#1374/PR #1377 before this story landed):** `ownTextColor`'s
`-webkit-text-fill-color` guard originally read `getComputedStyle`'s
resolved value in isolation, which real Chromium resolves to a concrete
color mirroring `color` for every element — never `""` nor the literal
string `"currentcolor"` — regardless of whether the property was ever
declared. The guard fired unconditionally, so `ownTextColor` returned
`"underdetermined"` before reaching any of `PG-FG-INHERITANCE-BOUNDARY`,
`PG-FG-NO-COLOR-SENTINEL`, `PG-FG-COLOR4-PARSE`, or
`PG-FG-ALPHA-COMPOSITE`'s own code — dead code against real page content,
exercised only by jsdom's own non-representative behavior for this one
property (jsdom preserves the literal `"currentcolor"` string instead of
resolving it). The landed fix compares the _computed_
`-webkit-text-fill-color` against the _computed_ `color` on the same
element instead of reading either in isolation: the two are always equal
when nothing overrides the fill (inline, stylesheet, or inherited), so the
guard now only fires when a real override is in effect, and the four rows
below execute normally otherwise. See `PG-FG-VENDOR-TEXT-FILL`'s own row
for the fix's full detail and its real-Chromium test coverage.

## Coherence check

Every `PG-*` row above has exactly one declared disposition and at least one
evidence owner or an explicitly named gap (`G-1`). This table went through
four rounds of Codex review while landing, each surfacing genuinely new
material about the underlying code, not merely refining prior fixes — every
finding below is confirmed by direct source inspection (and, for the most
severe one, an empirical test against this repo's own real Chromium, not
just reading), not taken on faith.

**The most severe finding this table's own review surfaced was #1374**
(priority:A, fixed in PR #1377 before this story landed): `ownTextColor`'s
`-webkit-text-fill-color` guard evaluated true for every element in real
Chromium, not just ones with an explicit override, making the entire
foreground-color audit return `"underdetermined"` unconditionally in
production — see the `PG-FG` section's own header and the
`PG-FG-VENDOR-TEXT-FILL` row for the full history and the landed fix. This
was qualitatively different from every other finding below: those are gaps
in an audit that otherwise functions; this one meant the audit's own
foreground-contrast computation never actually ran against real page
content in the browser this extension ships to. It was fixed ahead of
TSC-SF2/TSC-SF4 landing, per explicit direction, precisely because both of
those stories' own real-Chromium regression tests need a working foreground
channel to demonstrate a genuine before/after transition rather than
`"underdetermined"` in both states.

This PR's own review found five `unknown` rows (`PG-GEN-PSEUDO`,
`PG-SCOPE-IFRAME-CONTENT`, `PG-BG-INSET-SHADOW`, `PG-GEOM-ROOT-EXCLUDED`,
`PG-GROUP-MASK`) — silent gaps within an _audited_ scope, with
`PG-GEN-PSEUDO`'s own scope also broadened to cover `::marker` alongside
`::before`/`::after`. The first two were the epic's own headline findings;
TSC-SF2 (#1358) has since landed and closed both as bounded, explicit
`"underdetermined"` outcomes rather than silent gaps (see their own rows
above for the landed disposition). The other three (inset `box-shadow`; the
audit's own root element never being a candidate; a partial-alpha
`mask`/`mask-image`) remain open, tracked as #1371, #1372, and #1376 — none
is any existing story's scope, so each got its own sub-issue.

`PG-GROUP-BACKDROP-FILTER` (structurally implemented but untested) and
`PG-SCOPE-SHADOW-HOST-TRAVERSAL` (structurally implemented but currently
unreachable in production — see the `PG-SCOPE` section header, tracked as
#1370) are recorded honestly rather than silently counted as covered by
this table's existence. `PG-GEOM-RENDEREDNESS` was reclassified `sound` →
`heuristic` for an unhandled `visibility: collapse` case — a diagnostic
gap on invisible content, not a false `"legible"` on anything visible.
`PG-BG-OPAQUE` was also reclassified `sound` → `heuristic`; unlike
`PG-GEOM-RENDEREDNESS`, its gap is a genuine (if extremely narrow) false-
`"legible"` risk rather than pure imprecision, tracked as #1373.
`PG-FG-NO-COLOR-SENTINEL` was reclassified `sound` → `heuristic` for an
unhandled `color: transparent` + matching `text-shadow` case, tracked as
#1375, and a second variant found during #1377's own round-3 review
(`color: transparent` + `-webkit-text-fill-color: transparent` under
`background-clip: text`), tracked as #1378.

Closing any of #1370–#1376 or #1378 is outside TSC-SF1/#1357's own scope (a
documentation story), and none is claimed as done here.
